# 第二阶段：自动验证与修复闭环

本阶段继续第一阶段实现，接通聊天和任务续跑的收尾修复。

## 行为

1. 成功的开发任务进入自动验证，界面保持运行状态。
2. 分析/测试失败且属于代码失败时，将原始目标、验收条件、变更文件、差异和失败日志传给修复执行器。
3. 修复执行器仅能读取、搜索、创建和编辑工作区文件，写入沿用当前审批模式及读前写检查；使用后台网关的工作区租约和运行审计。没有终端、删除、移动或委派工具。
4. 修复成功后重跑原计划的全部检查，包括之前通过的检查。以实际结果更新审查、任务状态、通知和聊天最终回复。
5. 修复失败或中途取消时，清除旧验证计划和通过记录，将修复后的变更标为未验证。修复新增的文件也会纳入审查。

设置 → 受控工具清单：先开启“开发任务完成后自动验证”，再开启“验证失败后尝试修复”。后者默认关闭，不改变已有用户授权。关闭自动验证、文件权限或终端权限后，不会自动启动修复。

## 预算与停止条件

- `maxAutoAttempts = 2` 表示初始验证加一次自动修复后的重验，即最多自动修复一次；不是两次修复。
- 修复执行器最多 6 个模型步骤，每步输出上限为 4096 token（窗口不足时进一步缩小），使用当前配置的模型；未配置真实模型时不自动修复。避开了旧值 2048 被当作自动配置、对推理模型放大预算的行为。
- 权限错误与缺少运行环境不自动修复。普通断言里的 `missing` 或 `not found` 不再一概误分类为环境缺失。
- 尝试记录在模型调用前持久化，并绑定原 runId；重复收尾或重启恢复不会为同一运行重复发放修复次数。
- 模型返回“修好了”不代表通过，必须以重验结果判定。

## 验证与边界

相关开发循环、修复服务、聊天控制器与后台权限测试共 62 项通过。新增场景覆盖修复成功、再次失败、修复失败、取消、环境问题、权限问题、关闭开关，并验证同一运行的次数限制及已通过检查的重新执行。定向静态检查通过。

测试使用模拟运行时和修复回调，未调用真实付费模型、未执行真实外部项目脚本、未构建安装包。后台运行单独记录修复用量，聊天原回答的 token 数仍表示原模型回答的用量，不合并修复运行。

已经启动的单条验证命令仍按现有终端运行时的完成/超时机制退出；取消会阻止后续步骤和修复启动。修复阶段有工作区租约，但整段验证尚未统一持有跨阶段租约。符号索引、patch 事务、隔离并行子任务、统一折叠策略表仍为后续工作。
