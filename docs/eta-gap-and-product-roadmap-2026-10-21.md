# NEXUS 与 ETA 差距及双主线开发规划

日期：2026-10-21。用户已明确：保留“在手机上完成开发任务”的初心，同时保留 ETA 式通用手机助手能力。

本文记录首次代码与文档审阅后的规划建议，不是发布验收报告。首次审阅只新增本文；用户随后授权实施，首批改动及验收见[手机网页开发实施记录](mobile-web-development-delivery-2026-10-21.md)。

## 1. 产品定位

建议定位：**能完成日常事务，也能把想法开发成可运行成果的手机 Agent 工作台。**

两条主线共用已有执行、会话、任务、审批、记忆与结果系统：

- 通用助手：问答、当前页面理解、网页处理、系统操作、提醒、个人知识与跨应用任务。
- 手机开发：导入项目、理解代码、修改、运行、失败修复、预览、审查、提交和导出成果。

“手机开发”首先要有无需电脑的完整可用场景；可选电脑/服务器执行后端再承接重型构建。不能让连接电脑成为创建第一个网页或运行第一个脚本的前提。手机操作完整与所有编译计算都在手机本地发生，是两种不同承诺，产品应明确显示实际执行位置。

助手场景可使用开发能力处理数据和生成工具；开发场景可使用助手能力读取文档、核对界面并创建后续提醒。这种组合应成为特色。

## 3. 差距对照

| 方向 | ETA 已描述/实现的能力 | NEXUS 当前证据 | 判断与后续 |
| --- | --- | --- | --- |
| 通用 Agent 基础 | App 内统一 Loop、steering、暂停/取消、持久 transcript | `agent_executor.dart`、运行控制、恢复、工具管线、预算等已有；10-20 两轮整改已处理部分语义与分层问题 | 无需引入第二套 Runtime。继续收口职责与跨入口一致性 |
| GUI 跨应用 | 无障碍节点、手势、输入、窗口截图与用户接管；有系统版本条件 | 新无障碍服务明确只观察 NEXUS 自身窗口；不点击、不输入、不滚动 | 最大助手能力差距。已有 Android 系统动作/自动化规则不等于通用 GUI Agent |
| 系统入口 | 默认数字助理屏幕上下文；另有需 LSPosed/ROM 的厂商入口 | 默认助手服务、入口面板、单次文字核对进入草稿已存在；截图和连续语音未完成 | 先完善普通设备入口。区分主动取文、系统唤起截图、持续屏幕共享 |

| 远程开发 | 本文不将其视为已验证的 ETA 优势 | 自托管执行器原型和持久 API 已有，手机页仍只握手；默认宿主仅 diagnostic | 这是 NEXUS 自身重型开发目标的缺口。需要审批、项目快照、持久提交、重连查询及成果回传 |

## 5. 架构选择

保留 Flutter 的手机/桌面界面和现有 Dart Agent 核心，Android 原生桥继续承接系统专有能力。ETA 原生 Kotlin 的实现方式是参考，不构成重写理由。

在现有运行范围中明确：当前项目、可用工具、执行环境、审批范围和结果类型。助手任务默认聚焦当前输入和明确选择的数据；开发任务绑定项目、文件上下文和验证方案。跨场景使用工具须显式表达范围，不能因为选择“开发”就默认取得全部手机数据权限。

本地与远程是同一任务的不同执行后端；复用 runId、审批、取消、费用和结果记录。不得把电脑再做成与手机脱节的独立 Agent 系统。

现有终端逐次确认、敏感动作审批与未知结果不盲目重放的语义继续保留。ETA 的权限策略、默认开关和不设固定轮数是其产品选择，不自动适合本项目；长任务应通过预算可见、进度保存和明确续跑解决。

## 7. 建议采用的代表性验收场景

开发线：

1. 纯手机创建静态网页，预览、继续修改并导出。
2. 导入 Python 项目，复现失败、修复、运行检查，审查所改文件。
3. 导入 Node 项目，按需准备环境，启动本地服务，离开/返回后查看真实状态并停止。
4. 用现有小型 Java APK 技能生成成果，校验文件并交给用户确认安装。
5. 克隆已授权仓库、创建分支、修改、验证、选文件提交和推送。
6. 重型目标通过可选宿主执行，断网后重新查询同一任务并取回同一成果。

助手线：

1. 从当前页面选取内容，解释并生成提醒草稿，确认后查到真实提醒。
2. 在浏览器提取资料、整理为带来源的结果，再加入开发任务上下文。
3. 在明确授权的第三方测试 App 中观察、填写、确认结果并随时接管。
4. 在撤权、断网、切后台和重启后查看任务状态；已发生动作不会自动重放。

每个场景分别记录可用设备、构建版本、模型/价格、重试次数、手动操作次数、实际成果与失败原因。先测基线，再设成功率和耗时目标；不凭单元测试数宣称超过 ETA。

## 8. 最近两轮建议与暂缓范围

第一轮：B01–B03，加 D01 的“静态网页从需求到交付”垂直用例。重点检查复用现有入口、修复断点，避免新建大量页面。

第二轮：D02 本地 PTY 与 D03 Git，推进 D04 的 Python/Node 场景；同时完成 A02 的跨应用控制设计，再进入 A03 实施。

持续保留已有助手能力。暂缓大范围 ROM 私有数据适配、全套 LSPosed 入口、角色扮演生态、实时音视频以及新的全局 UI 重写；这些不会先于开发交付链路和高频助手任务证明核心价值。

模拟器用于 Android UI 与通用交互。ARM64 PRoot、本地工具链、厂商后台策略和功耗仍需要相应真机证据；后续实施须遵守当时有效的设备与模型调用授权，本次规划没有执行这些操作。
