# NEXUS 桌面端评估与开发路线

日期：2026-10-15。范围：当前本地工作区的 Windows Flutter 桌面端，包括尚未提交的实现。

## 结论

NEXUS 已具备 Agent 工作台的核心骨架：多模型、流式对话、计划与审批、文件工具、Git 差异与暂存、网页预览、任务记录、恢复、MCP、知识库和设备连接。下一阶段最有价值的工作是把已有能力接成稳定、可发现、可验证的桌面流程。

建议定位为“以项目为中心、可审查和恢复的 Windows Agent 工作台”，主线为：打开项目 → 描述任务 → 确认计划 → 执行与审批 → 审查改动 → 验证结果 → 接受或恢复。Android 设备协同作为差异化能力保留，桌面主流程围绕项目任务展开。

优先顺序：恢复可靠性与功能接线 → 桌面交互和布局 → 性能测量与优化 → 工作流和分发完善。继续使用 Flutter 有合理基础；本次没有证据支持为了流畅性重写技术栈。

## 已有基础应当保留

- 桌面三栏布局、面板尺寸持久化、宽窄窗口适配、浅深主题已实现。
- Git 差异、文件暂存/取消暂存、预览、文件引用均接入实际服务。
- 会话列表分页、消息懒构建、Riverpod 的局部订阅、流式 Markdown 扫描缓存已经存在。
- 终端输出已有 150ms 合并刷新；动效系统已有帧耗时采样与降档机制。
- Windows 更新包选择、下载校验、错误提示，以及 CI 中 Windows 构建均已有基础。

所以后续开发不应重复立项“增加 Git”“增加流式”“增加分页”“增加减少动态效果”。应检查现有实现的接入、边界与真实用户操作路径。

## 发现与优先级

### P0：恢复操作必须先保证一致性

**确定的代码路径问题：同时回退代码和会话时，即使代码恢复存在冲突，仍然删除后续消息。**

位置：[desktop_checkpoint_timeline.dart](../lib/presentation/navigation/desktop_checkpoint_timeline.dart)，`_rewind` 的 both 分支约 145 行。调用 `_rewindCode` 后立即 `_rewindConversation`，随后才把冲突附加到提示文字。

影响：工作区只恢复了一部分，但用于理解剩余改动的对话已被截断。该结论来自控制流检查，本次未通过真实用户数据触发该操作。

建议：先做恢复预检，展示会影响的文件与会话范围；有冲突时保留消息并进入冲突处理。恢复过程中锁定对应会话的写入和工具执行。恢复完成后统一刷新消息、任务、Git 与时间线。

另外，时间线读到了 `running`，但回退菜单仅用 `_busy` 禁用，未阻止在运行期间回退。应在服务层校验对应会话的运行状态，而不仅依靠按钮状态。

验收：无冲突全量恢复、用户自行改文件引发冲突、执行中触发恢复、恢复期间切换会话、恢复失败后重试。冲突场景不得自动截断会话。

### P1：把已经写好的功能接到真实入口

**worktree：已有服务和徽标，没有完整产品接线。**

位置：[desktop_worktree_service.dart](../lib/application/desktop_worktree_service.dart) 的 `ensureSessionWorktree`、`removeSessionWorktree`；[app_shell.dart](../lib/presentation/navigation/app_shell.dart) 的 `_newConversation`。

当前检索中创建/删除会话 worktree 的调用只有测试，应用中新建会话没有调用它们。侧栏根据当前目录显示 worktree 标记，不能证明会话已经获得隔离工作区。

建议顺序：创建会话选择“当前目录/独立分支” → 创建 worktree → 持久化会话与目录关联 → 工具/终端/预览统一绑定 → 展示状态 → 完成后比较、合并或归档 → 清理前检查未提交改动。已有删除服务的 `force` 默认值是 true，接入 UI 前应改成默认保留未提交工作。

**命令中心：新组件已有测试，但 Ctrl+K 仍打开旧列表。**

位置：[desktop_command_center.dart](../lib/presentation/navigation/desktop_command_center.dart) 与 [app_shell.dart](../lib/presentation/navigation/app_shell.dart) 的 `_showCommandPanel`，约 379 行。

`DesktopCommandCenter` 在 lib 中仅找到自身定义；实际入口仍构建 `SimpleDialog`，搜索则走另一套 `showSearch`。

建议：接入现有组件，统一命令注册；Ctrl+K 搜命令，Ctrl+P 聚焦项目/会话/文件。补“从真实快捷键触发、输入、上下键选择、回车执行、Esc 返回”的测试。组件单测继续保留，但验收以真实入口为准。

### P1：桌面输入与选择应当自然

位置：[message_bubble.dart](../lib/presentation/chat/widgets/message_bubble.dart) 约 74、153、569 行。

当前正文默认不可选，消息菜单依赖长按；选择文本要先进入单独模式，且以纯文本呈现。适合触摸端的折中影响了桌面常见的拖选、复制和右键操作。

建议：桌面正文默认可拖选；右键提供复制、编辑重发、重新生成、引用与分叉；悬停显示低强调操作条；保留格式化内容的选择行为。追加文件拖放、粘贴图片、文件路径引用和明确的附件状态。

验收：鼠标直接拖选中文段落；右键不会破坏选区；Ctrl+C 复制选择内容；输入框中文 IME 确认不误发；键盘能到达全部主要操作。已有 Enter/Shift+Enter 测试不能替代中文输入法实机验收。

### P1：重新分配首页空间，统一设置页

观察依据：当前桌面渲染图及 [app_shell.dart](../lib/presentation/navigation/app_shell.dart) 约 105、572 行，[desktop_workbench_service.dart](../lib/application/desktop_workbench_service.dart) 的布局默认值。

空会话默认打开工作台和终端；在宽屏“改动”页内部还嵌入预览。1440×900 图中右侧占据大量空间，差异内容只剩较浅区域。左侧把会话称为“任务”，同时还有独立任务入口，概念存在混淆。

建议三个可记忆布局：

| 布局 | 默认呈现 | 自动提示时机 |
| --- | --- | --- |
| 专注 | 项目/会话侧栏 + 对话，右侧和终端收起 | 有待审批或产物时显示明确入口 |
| 执行 | 对话 + 活动步骤；终端按需展开 | 用户打开运行输出时 |
| 审查 | 文件列表 + 足够大的 diff；对话可收窄 | 任务完成后用户选择“查看改动” |

保留用户选择，不因每个工具调用强制切换布局。预览和 diff 各自拥有完整工作区域，避免常驻重复预览。

设置页仍是手机式单列卡片，并直接展示 Root、Termux、SAF、通讯录等项目。证据：[settings_page.dart](../lib/presentation/settings/settings_page.dart) 约 595–625 行及设置截图。

建议桌面设置改为左侧分类、右侧表单；分类为模型、项目与执行、工具与 MCP、外观与快捷键、数据与更新。手机能力归入“已连接 Android 设备”，按实际连接与支持状态显示。项目、会话、运行任务使用一致名称与状态定义。

### P1：无障碍和动效需要验证实际使用链路

高对比度判断在 [desktop_theme.dart](../lib/presentation/theme/desktop_theme.dart) 的 `of` 中；实际桌面组件普遍使用 `maybeOf`，后者仅返回主题扩展。`DesktopFocusRing` 当前只找到定义与测试，没有生产调用。不能把辅助组件测试通过等同于整个桌面已适配高对比度和焦点环。

`reduceMotion` 使用两个 bool 的 `??` 链，前一个返回 false 时不会继续判断 `accessibleNavigation`。若设计意图为任一条件成立即减弱动画，应使用逻辑或并补组合场景测试。

主面板的 `AnimatedContainer` 受 `_layoutEdited` 控制；该字段保存布局后持续为 true，且关闭侧栏是条件移除子树。这不足以构成稳定的面板进出动画。需要把“正在拖拽”与“设置已被用户修改”拆成两个状态。

建议动效规范（产品目标，非竞品测量值）：

| 交互 | 建议时长 | 目的 |
| --- | --- | --- |
| Hover、按下、焦点反馈 | 80–120ms | 立即确认交互对象 |
| Tab 与选中态切换 | 120–160ms | 清晰表达当前选择 |
| 面板展开/收起、状态卡切换 | 160–220ms | 保持空间关系 |
| 新消息进入 | 120–180ms，轻微淡入/位移 | 提示新增内容；流式更新不重复入场 |
| 拖拽分隔栏 | 无补间延迟 | 跟随指针 |
| 减少动态效果 | 位移/缩放关闭，保留即时状态 | 保持功能可用 |

将已有动效系统和桌面规范接起来。常驻粒子、大面积模糊、文字逐字装饰动画暂不列为下一版重点。

### P1：建立可复现的性能基线

当前有懒列表、流式扫描缓存和帧降档，仍不能据此判断长会话流畅性达标。

三个具体待测热点：

1. [streaming_markdown.dart](../lib/presentation/chat/widgets/streaming_markdown.dart) 约 44–55 行：稳定内容增长时整体 stable 字符串变化，重新创建整个稳定区的 Markdown 子树。扫描增量化不等于渲染块增量化。`DeferredMarkdown` 推迟到下一帧，也没有把解析移出 UI isolate。
2. [terminal_sheet.dart](../lib/presentation/workspace/terminal_sheet.dart) 约 132–144 行：输出合并后仍持续拼接 `_output` 大字符串，UI 层未见显示窗口截断。应结合底层作业日志上限，测试长输出；考虑环形显示缓冲、逐行虚拟化、完整日志落盘和按需加载。
3. [motion_tier.dart](../lib/presentation/motion/motion_tier.dart)：降档判定最低使用 16.7ms，因此不能证明 120Hz 的 8.3ms 帧预算达标。现有机制用于降级装饰效果，另建真实刷新率下的性能报表。

`tool/benchmark_streaming_markdown.dart` 明确是 scanner 的宿主 JIT 微基准，不测 Flutter 布局、光栅或输入响应。

建议在固定 Windows 机器的 profile/release 模式记录 CPU/GPU、DPI、刷新率、数据集、预热和采样区间。分别记录：

| 场景 | 数据集 | 第一阶段验收目标（待基线校准） |
| --- | --- | --- |
| 本地冷启动 | 无模型请求，分别测有/无历史数据 | 可交互时间 ≤2 秒 |
| 输入、滚动、拖拽 | 长会话同时模拟流式输出 | 输入回显 p95 ≤50ms；60Hz 下 UI/Raster p95 各 ≤16.7ms |
| 会话切换 | 100/1,000/5,000 条消息 | 本地内容呈现 p95 ≤300ms；不等待模型联网 |
| 流式 Markdown | 2k/10k/50k 字符，含代码、表格、未闭合代码围栏 | 记录重建次数、解析时间、卡顿比例；优化前后同数据比较 |
| 长终端输出 | 10 万行日志 | 滚动与输入可用，显示缓冲和内存有界 |
| 面板生命周期 | 反复切换项目、WebView、终端 30 次 | 内存回收后趋势稳定；无孤儿服务与退出挂起 |

目标数值是建议门槛，不是当前测量结果。模型首 token 延迟与本地 UI 延迟分开统计；后者不能被网络等待掩盖。

### P2：终端、审查和预览形成完整工作流

**终端。** 当前 Windows `HostProcessRuntimeAdapter` 明确 `supportsShellSyntax=false`，命令解析还有限制；内嵌面板主要是命令输入与输出查看，不能等同于持久交互终端。依赖 `xterm` 不代表 Windows 已接通 ConPTY。

建议将 Agent 的受控命令执行和用户的交互终端分开建模。补 Windows ConPTY、持久 shell、stdin、ANSI、窗口尺寸、中文编码、Ctrl+C、进程树终止与启动失败诊断。未完成前，可清楚标为“命令运行器”，并提供在外部终端打开项目。

**审查。** [DesktopDiffView](../lib/presentation/navigation/desktop_review_panel.dart) 当前按 diff 文本行索引显示行号，不是源文件的新旧行号。增加 hunk 解析、双列行号、定位文件、差异折叠；后续增加逐块接受/恢复和语法高亮。已有逐文件暂存继续保留。

**任务结束。** 建立统一结果面板：修改文件、验证命令及退出码、产物、失败/跳过项、检查点。每个结论能打开实际证据，未执行的测试不能呈现为成功。

**预览。** 当前需手动启动开发服务器并填 URL。增加项目运行配置、启动/停止、端口检测、日志关联和失败重试；遵循既有执行授权。任务产物可直接跳转预览。

### P2：运行生命周期与分发

Windows ZIP 下载与校验已有实现，当前升级仍需要手动解压。后续增加安装器、WebView2 依赖诊断、升级前检查与版本回退验证。数据迁移和应用版本回退必须分别设计。

README 明确 Windows 不使用 Android 的后台调度。若桌面主打定时任务，应先定义“窗口关闭、退出进程、系统休眠、重新登录”各状态下的承诺，再实现托盘驻留/后台运行和通知；无需继承手机端语义。

项目已有桌面测试与 CI 构建。下一步增加真实入口端到端回归、原生退出/子进程清理、多 DPI、多显示器、代理网络、WebView2 缺失与安装升级验收。建立桌面专用的发布清单。

## 建议开发节奏

以下按一名熟悉项目的全职开发者粗估，具体取决于原生终端与性能排查结果；每阶段通过验收后再进入下一阶段。

| 阶段 | 建议周期 | 交付 | 出口条件 |
| --- | --- | --- | --- |
| A：完成已有功能闭环 | 约 1 周 | 检查点冲突保护、运行中恢复保护、命令中心接入、worktree 创建与绑定最小流程 | 从真实界面可完成；冲突不丢会话；隔离目录一致 |
| B：桌面体验统一 | 约 1–2 周 | 专注/执行/审查布局、桌面设置、鼠标选择和右键、统一语义色和焦点、轻量动效 | 浅深色、900/1280/1440 宽度及 125%/150%/200% DPI 可用；键盘与 IME 验收 |
| C：性能与开发闭环 | 约 2–3 周 | 性能基线、Markdown 与日志热点优化、diff 真实行号、运行配置、结果与证据面板；交互终端单独估算 | 性能数据可复现；典型任务从输入到审查和恢复完整跑通 |
